# 信盾 TrustShield 方案设计文档

> 面向东江集团“信审与合同评审”命题 ｜ 版本：v1.0 ｜ 日期：2026-08-03

## 1. 建设背景与设计目标

制造企业的合同风险并不只存在于合同文字本身。合同金额、账期、预付款、付款方式和 VMI/JIT 等条件，一旦超出客户已批准的授信条件，就会形成跨部门、跨流程的经营风险。传统流程通常由业务、法务、财务分别查看材料和填写表单：信审结论难以成为合同端的机器可执行约束，合同审查又往往停在“生成一份风险报告”，催办、回退、补件和审批仍依赖人工追踪。

信盾的目标是把“人工串联的静态流程”升级为“**Agent 受约束地自主推进、规则强制兜底、人在关键节点负责**”的协同闭环：

1. 先由客户信审建立可执行的信用边界；
2. 再由合同审查自动将合同事实与该边界逐项对照；
3. 越界时自动阻断、定位证据并引导回到正确的信审或修订路径；
4. 人工只在证据核验、条件修订、例外审批和最终签约节点行使决策权；
5. 让 Agent 行动、模型依据、规则结论、人工决策和文档导出均形成可追溯审计链。

## 2. 业务创新：从“合同问答”到“自主流程协同”

| 传统业务流程 | 信盾的自主化改造 | 业务价值 |
| --- | --- | --- |
| 审核人员反复翻阅财报、信用材料和历史敞口 | 信审 ReAct Agent 在受控只读证据范围内自主决定下一步检索、页表上下文读取、Claim 核验或补件请求 | 减少材料查找与反复沟通，保留每项事实来源 |
| 授信结论停留在 Word、邮件或台账 | 已生效信审版本被固化为额度、账期、预付款、付款方式和交付模式等可执行边界 | 商业条件可被系统消费，不依赖人工记忆 |
| 合同工具只报告风险，后续靠人工跟进 | 合同 Agent 完成解析、脱敏、候选召回与语义研判；规则引擎自动门控并生成下一责任人的待办 | 从“发现问题”延伸到“推动问题闭环” |
| 业务可用备注或合同例外绕过授信 | `CREDIT_*` 越界项不可在合同端忽略、采纳或普通审批覆盖，必须更新信审后复审 | 将风险控制前置为硬门禁 |
| 过程记录分散在邮件、群聊和文件夹 | 案件、版本、风险处置、审批、导出和归档统一记录审计日志 | 满足复盘、问责和持续优化需求 |

这里的“自主”并非让模型自行批准额度或签约。Agent 只能在预先定义的权限和工具范围内读取、检索、归纳、校验、发起待办与给出建议；额度生效、合同例外、签约和归档仍由具备权限的人员通过工作流完成。

## 3. 总体方案

```text
客户/财务材料、CRM/ERP 敞口、合同及附件
                 │
                 ▼
本地解析与脱敏 ──► 受控证据资产 / 加密映射
                 │
        ┌────────┴────────┐
        ▼                 ▼
信审 ReAct Agent      合同审查 Agent
证据检索与 Claim      条款解析、候选召回、语义研判
核验、补件请求       与信用边界逐项对照
        │                 │
        ▼                 ▼
评分卡、人工复核       确定性底线规则 + CREDIT 门禁
        │                 │
        └─────► 已生效信审边界 ◄─────┘
                         │
                         ▼
角色待办、补件、例外审批、版本复审、导出与归档审计
```

系统由 React 前端、FastAPI 服务、SQLite 加密存储和受控模型适配层组成。开发模式使用 Vite 前端和 FastAPI 后端；生产模式构建前端后由后端直接托管静态文件，可单服务部署。

## 4. 核心设计

### 4.1 信审 Agent：证据驱动的自主核验

信审 Agent 接收的是文件画像、已解析的文字/表格/OCR 块、敞口快照与案件上下文，而不是不受约束地直接读取数据库。其执行循环为：

```text
材料画像 → 判断待核验事实 → 检索候选证据 → 读取页/表上下文
    → 提交带原文锚点的 Claim → 确定性校验主体/期间/单位/币种/时效
    → 继续核验 / 请求补件 / 结束
```

- Agent 仅有材料画像、检索、证据上下文、只读敞口、已验证 Claim 和 Claim 比较等只读工具；
- 每个核心事实必须携带来源块、引文、原始数值、币种与单位；不能在来源中核验的内容不进入评分；
- 材料不足、模型不可用或关键 Claim 缺失时，系统失败关闭为 `not_assessable` 或 `execution_failed`，不伪造评分和授信建议；
- 完整事实再进入版本化评分卡，审核专员可确认或修订建议，之后按主管、最终审批人路由生效。

### 4.2 合同审查：Agent 与确定性规则各司其职

合同链路以案件管理主合同、附件和修订版本。上传后依次完成文件解析、本地规则脱敏、字段提取、候选规则召回、语义研判、确定性底线校验及信审边界核验。

| 能力 | 责任机制 |
| --- | --- |
| 解析与字段识别 | 支持 DOCX、PDF、XLSX、TXT 和图片；扫描件可使用本机 OCR |
| 脱敏 | 规则脱敏覆盖电话、邮箱、证件、账户、地址、金额、公司、图号和联系人；可配置智能脱敏补足残余实体；映射加密保存 |
| 语义研判 | Agent 负责候选条款召回、否定/例外/义务关系识别和修改建议，输出必须附原文锚点 |
| 底线裁决 | 账期、有效期、付款、VMI/JIT、责任等封闭规则由代码确定性判断，不依赖模型“感觉” |
| 信审联动 | 检查额度、账期、最低预付款、付款方式和 VMI/JIT；`CREDIT_*` 越界为不可绕过阻断 |

### 4.3 工作流与人工协同

| 角色 | 主要责任 | 系统支持 |
| --- | --- | --- |
| 业务申请人 | 发起案件、补件、上传修订版 | 申请入口、状态查询、补件待办 |
| 信用审核专员 | 核验证据、处理风险、提交复核 | Agent 运行轨迹、证据、风险工作区、处置记录 |
| 财务审批主管 | 判断差异与中层审批 | 差异对比、审批路由、退回与上报 |
| 最终审批人 | 重大例外与最终商业边界决策 | 完整审计依据、终审动作 |
| 系统管理员 | 用户、规则、路由和运行配置治理 | 权限、版本化规则、连通性测试、审计查询 |

状态由领取、补件、提交审批、批准、退回、拒绝、确认可签和归档等业务动作推进，不能直接编辑状态字段。签约导出前再次执行门禁，避免报告生成后因条件变化而误放行。

## 5. 数据安全与治理

1. 原文文件、解析资产、映射、审查报告和人工处置记录放在受限目录；敏感持久化字段使用 Fernet 加密。
2. 规则层先进行本地脱敏，远端审查模型只接收脱敏后的文本；翻译外发前强制检查脱敏映射，缺失映射即拒绝。
3. 财务证据的外部检索/重排授权独立控制，默认预填阿里百炼配置并开启授权（便于开箱即用）；在填入 API Key 前不会发生任何数据外发，企业合规策略可随时在系统设置中关闭授权开关。外发到 Embedding / 重排 / 财务模型服务的证据文本必须先经本地脱敏模型（正则 + 本地 LLM，默认本地 Ollama）掩码，无可用脱敏模型时拒绝外发，模型仅接触掩码文本，占位符由本地还原校验。
4. 模型不拥有写入授信条件、批准例外或导出签约稿的权限；合同端不能覆盖已生效信审边界。
5. 用户、角色、案件动作和审批流均在后端鉴权；前端展示不替代服务端授权。
