# ContractGuard 从零实跑操作说明

> 适用版本：当前仓库实现 ｜ 场景材料：`docs/03-演示与交付/模拟测试材料/` ｜ 数据属性：全部为虚构、脱敏的演练数据。

这是一份面向第一次操作人的点击式说明。完成后，您会得到一条已生效的客户信审 V1、一个被信审拦截的风险合同案件、一份修订合同的复审记录，以及相应的审批、导出与审计证据。

本说明把“量化 Agent 成功”和“量化 Agent 未配置或失败”分开处理：两种情况都能验证状态机与信审前置控制，但不能把失败的模型结果伪装成自动通过。

## 1. 演练目标与角色

本次采用下列固定的、可复核的商业边界：

| 项目 | V1 生效条件 |
| --- | --- |
| 客户 | 远辰汽车零部件（模拟）有限公司 |
| 信审业务类型 | `TKP`（注塑组件制造） |
| 总敞口上限 | CNY 1,000,000 |
| 最长账期 | 45 天 |
| 交付前最低收款 | 30% |
| 允许付款方式 | 银行转账（`bank_transfer`） |
| VMI/JIT | 不允许 |

建议使用四个独立账号。系统不支持同一个账号“切换角色”；演练时请退出后以对应账号重新登录。

| 账号角色 | 系统角色值 | 本次操作 |
| --- | --- | --- |
| 系统管理员 / 集团财务总监 | `admin` | 初始化人员；完成信审最终批核；必要时处理集团财务总监级合同例外。 |
| 信用审核专员 | `reviewer` | 创建及评估信审、上传材料、保存敞口、确认报送依据、送主管复核、领取/复核合同。 |
| 财务审批主管 | `director` | 复核信审；处理主管级合同例外或合同案件审批。 |
| 业务申请人 | `business` | 发起合同案件、上传主合同与修订版、响应补件。 |

### 一条主线看完整流程

合同案件是全部合同动作的唯一入口；不要分别在报告、案件列表和工作台中猜测下一步。每次进入案件详情，优先查看顶部的“当前版本通关检查”：它会按**信审边界、合同风险处置、待补材料、条款例外审批**四类门禁告诉你谁该处理什么。

```text
business：创建案件、绑定已生效信审、上传合同 / 修订版、响应补件
    ↓ 系统审查完成
reviewer：核对风险证据、处理风险、确认材料、决定可签约或提交主管
    ↓ 有主管级事项时
director：处理主管审批 / 条款例外，决定通过、退回或上报
    ↓ 需要终审时
admin：完成最终审批
    ↓
reviewer：归档已签约案件
```

修订版本通过审查后会成为“当前版本”；旧版本仅保留用于对比和审计，旧版本遗留的审批或补件不应继续阻塞当前版本。

本演练的标准路径是“先修订合同文本，再复审”，所以不需要真的通过合同例外审批放行风险合同。`CREDIT_*` 信审阻断不能由任何合同端审批覆盖。

## 2. 启动前检查

### 2.1 安装与基础配置

需要 Python 3.11+、Node.js LTS 和 npm。第一次运行时，在仓库根目录执行以下命令安装依赖：

```powershell
Set-Location .\backend
python -m pip install -r requirements.txt
Set-Location ..\frontend
npm install
Set-Location ..
```

建立本机启动配置；`backend/.env` 不应提交到 Git，也不要把密码或密钥写入本材料包。

```powershell
Copy-Item .\backend\.env.example .\backend\.env
```

在 `backend/.env` 至少填写以下值：

| 配置 | 用途 |
| --- | --- |
| `AUTH_SECRET` | 登录令牌签发密钥；可用 `python -c "import secrets; print(secrets.token_urlsafe(48))"` 生成。 |
| `DATA_ENCRYPTION_KEY` | 本地加密密钥；可用 `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"` 生成。 |
| `INITIAL_ADMIN_USERNAME`、`INITIAL_ADMIN_PASSWORD`、`INITIAL_ADMIN_NAME` | 第一次空库启动时创建的管理员。密码至少 10 个字符。 |

模型 URL、模型名和 API Key 不填进 `.env`。管理员登录后在左侧 **系统设置** 维护模型配置；**组织与规则** 只用于成员、规则、审批路由和审计日志。要验证完整生产量化链路，页面的“财报 ReAct 模型”和“证据精排”均应显示已就绪；Embedding 可选，若已启用也必须显示已就绪。

### 2.2 决定是否从空库开始

先停止正在运行的本地后端，然后按 [00-实跑前清理与协作规则.md](./00-实跑前清理与协作规则.md) 的只读检查确认是否已有信审、合同或上传件。

- 若要保留历史演练：不要清理，改用一个未使用过的模拟客户名；同一客户每次新建都会递增版本号。
- 若要严格复现下文的“V1”：按该文第 2 节只清理数据库、WAL/SHM 和 `uploads/` 内容。绝不删除 `backend/data/config.json`、`backend/data/tessdata/` 或本材料目录。

### 2.3 启动和登录

在仓库根目录运行：

```powershell
.\dev.ps1
```

脚本会分别打开后端和前端 PowerShell 窗口。浏览器访问 `http://127.0.0.1:5173`，以初始管理员登录。右上角“模型在线/模型未配置”只是主模型连通状态；信审是否可做生产评估，以“客户信审”详情内的运行环境提示为准。

在“组织与规则”创建 `reviewer`、`director`、`business` 三个账号。用户名至少 3 个字符，密码至少 10 个字符。分别退出并登录一次，检查菜单是否符合下表：

| 登录角色 | 必须看到的入口 |
| --- | --- |
| `reviewer` | 我的工作台、合同案件、客户信审、风险矩阵、条款知识库 |
| `director` | 我的工作台、合同案件、客户信审、风险矩阵 |
| `business` | 我的工作台、合同案件、客户信审、发起合同申请 |
| `admin` | 我的工作台、合同案件、客户信审、风险矩阵、系统设置、组织与规则 |

**停点 A：** 记录本次演练日期、四个账号（不记录密码），并在“客户信审”“合同案件”中确认是否为空。若不为空，确认您是继续历史数据还是已按规则重置；不要混用两种结果。

## 3. 先完成客户信审 V1

以下步骤由 `reviewer` 完成，除审批步骤外不要切换角色。

### 3.1 创建草稿并补齐输入

1. 打开左侧 **客户信审**，点右上角 **新建信审版本**。
2. 按 [01-信审申请单.md](./01-信审申请单.md) 填写客户、申请说明和下列字段：
   - 客户名称：`远辰汽车零部件（模拟）有限公司`；
   - 业务类型：`TKP`；币种：`CNY`；
   - 申请最大单笔/敞口金额：`1000000`；最长账期：`45`；交付前最低收款：`30`；
   - 允许付款方式仅选“银行转账”；“允许 VMI/JIT”选“不允许”。
3. 点 **保存评估草稿**。列表中应出现 V1、状态“待信用审核专员评估”。点客户名称或“量化评估”打开详情抽屉。
4. 在“材料与交易敞口”区域，文档类型选“客户财报”，上传 `02-客户财务报告-模拟.txt`。推荐使用 TXT；如要演示 Word 解析，可改上传同内容的 DOCX，但一次信审只上传一个版本。
5. 在 CRM/ERP 敞口快照中，按 [03-CRM-ERP敞口快照-模拟.json](./03-CRM-ERP敞口快照-模拟.json) 填写并保存：

| 字段 | 值 |
| --- | ---: |
| 当前应收 | 100,000 |
| 已入单金额 | 200,000 |
| 逾期金额 | 0 |
| 最长逾期天数 | 0 |
| 币种 | CNY |

**停点 B：** 在详情页核对客户、V1、财报“文字资产已保存”状态和敞口快照。既有敞口必须是 100,000 + 200,000 = CNY 300,000；币种或逾期天数填错会改变后续结果。

### 3.2 运行评估并固化报送依据

点 **运行量化评估**，等待“量化 Agent 正在运行”消失。以下两条路径二选一；不应跳过此步骤直接送审。

#### 路径 A：生产 Agent 成功

满足以下条件时，评估结果可以直接作为建议：评估状态为完成、审计引擎显示 `production · ReAct`、模型状态为 `ready_for_reviewer`，且没有高风险制度阻断。

1. 查看评分卡、已验证 Claims、来源证据、风险/补件和建议条件，确认核心财务事实和敞口的口径可解释。
2. 若系统建议恰好就是本说明第 1 节的 V1 条件，点 **应用建议到草稿**。页面会标记“采用 Agent/模型建议”。
3. 若建议不同，但您有授权按本演练的保守条件报送，不点“应用建议”，转到“审核专员确认与修订”，填写 V1 条件和 [01-信审申请单.md](./01-信审申请单.md) 第 4 节的人工依据，点 **保存人工确认/修订依据**。

#### 路径 B：模型未配置、超时或评估失败

此时页面应显示“评估失败”或“未形成授信评分或建议”，这是失败关闭，不是通过。保留运行记录，然后：

1. 检查运行环境提示、材料解析状态、模型配置和证据精排配置；不要伪造评分、Claims 或自动建议。
2. 若您确有人工核验的业务授权，在“审核专员确认与修订”填写第 1 节的 V1 条件，并在“审核专员修订/兜底依据”粘贴 [01-信审申请单.md](./01-信审申请单.md) 第 4 节说明，再点 **保存人工确认/修订依据**。
3. 页面应标记为“Agent 异常/不适用的人工报送”。这条路径仍会保留失败评估和人工理由，不能称为模型自动审批。

无论哪条路径，看到“待审核专员确认”时均不能送审。只有保存了“采用 Agent/模型建议”“审核专员修订后报送”或“Agent 异常/不适用的人工报送”之一，列表才会显示 **送主管复核**。

**停点 C：** 截图或记录评估状态、报送依据、最终 V1 条件和审核专员理由。重点确认没有把缺失材料或高风险提示误当成可直接应用的 Agent 建议。

### 3.3 信审审批到已生效

1. `reviewer` 点击 **送主管复核**。状态变为“待财务审批主管复核”。
2. 退出后以 `director` 登录，打开 **客户信审**，对该 V1 点 **复核通过**，填写主管意见（可使用 01 文件中的示例）。
3. 默认审批路由下，本案会进入“待集团财务总监最终批核”：本演练 30% 预付款以及人工修订/兜底（如有）都会命中默认上报条件。以页面显示的“路由原因”为准；管理员若发布过自定义审批路由，实际是否终审可能不同。
4. 若状态为“待集团财务总监最终批核”，退出后以 `admin` 登录，点 **最终批核** 并填写最终意见。
5. 最终状态必须为“已生效”（系统值 `approved`）。只有此状态的版本才会在合同申请中被选择。

**停点 D：** 记录 V1 的状态、主管/终审意见、路由原因和 `case_id`。不要手工改合同页面中的额度、账期或客户来替代这份已生效信审。

## 4. 提交风险合同，验证信审前置阻断

此步骤应使用 `business`，因为“发起合同申请”只向业务申请人展示。

1. 登录 `business`，打开 **发起合同申请**。
2. 填写客户名称，必须与 V1 完全一致；离开输入框后系统会加载已生效信审版本。若下拉框为空，点“刷新该客户信审版本”，再检查 V1 是否仍为已生效且未失效。
3. 选择 V1；合同业务类型选择 **模塑一体**，优先级选“普通”，申请说明可写“验证信审边界与合同底线规则”。信审业务类型的 `TKP` 与合同规则路由的“模塑一体”是不同维度，允许这样选择。
4. 上传 `04-风险合同-待审.docx`，它必须是列表中的第一份文件（主合同），再点 **创建案件并提交审查**。
5. 页面会跳转至案件详情，先显示“AI 审查中”。等待变为“信用审核专员复核”，在“文件与版本”中打开 V1 主合同的 **查看报告**。

**必须观察的五项 `CREDIT_*`：**

| 规则 | 样例合同事实 | 预期 |
| --- | --- | --- |
| `CREDIT_TERM` | 60 天付款（文本还含 120 天的底线风险） | 超过 V1 的 45 天。 |
| `CREDIT_PREPAYMENT` | 20% 预付款 | 低于 V1 的 30%。 |
| `CREDIT_PAYMENT_METHOD` | 银行承兑汇票 | V1 仅允许银行转账。 |
| `CREDIT_DELIVERY_MODE` | VMI | V1 禁止 VMI/JIT。 |
| `CREDIT_EXPOSURE` | 800,000 合同额 + 300,000 既有敞口 | 合计 1,100,000，超过 1,000,000。 |

报告总体结论应为“信审阻断·须先更新信审条件”。对 `CREDIT_*` 项，报告只会显示“仅可更新信审后复审”，不能采纳、忽略或走合同侧例外审批；修订建议稿和双语稿也会被拒绝导出。原文版可以仅作留档对照，不能视为可签约文件。

同时观察合同底线风险，如 R03 承兑汇票、R04 连带责任、R05 排他、R06 无责取消、R07/R08 质保、R09 法律识别、R10 赔偿、R11 期限、R12 间接损失、R13 关联方外溢、R14 知识产权、R15 价格、R16 VMI。确定性规则优先稳定命中部分条款；其余由候选召回、模型研判和人工证据复核共同确认。

**停点 E：** 在报告中记录至少五个 `CREDIT_*` 规则及其证据，不要对风险合同执行“确认可签约”“主管批准可签约”或导出修订建议稿。

## 5. 用修订合同复审

这一步验证“合同改回已生效信审边界”而不是在合同端放宽信审。

1. 仍以该案件创建人 `business` 登录，打开 **合同案件**，进入刚才创建的案件。
2. 点击 **上传修订版 / 补充文件**，上传 `06-修订后合同-复审.docx`。若案件处于“待业务补件”，系统会先将案件切回审查中；上传后会成为同一案件的 V2 文件版本。
3. 等待 V2 审查完成，打开 V2 的报告；在“版本对比”页签选择 V1 和 V2，点 **开始对比**。
4. 核对修订合同：合同总价 CNY 600,000，与既有敞口 CNY 300,000 合计 CNY 900,000；账期 45 天；交付前收款 30%；银行转账；明确约定**不采用** VMI/JIT。
5. V2 报告中不得再出现 `CREDIT_*`。明确写有“不采用 VMI/JIT”的否定条款不应被当作采用 VMI；若仍出现，请先定位合同文字、币种、客户名称或敞口快照，不要忽略风险。

合同底线事项仍要由人工基于原文证据处理：可直接采纳建议、编辑建议或补充材料；确需保留例外时，按 [05-例外审批说明-模拟.md](./05-例外审批说明-模拟.md) 发起条款审批。注意：本样本的 30% 交付前收款符合信审 V1 的 30% 下限，但低于模塑一体 R01 的 60% 合同底线；它不是 `CREDIT_*` 阻断，仍必须由审核员留痕处置。若要演示“无合同风险直接通过”，请将合同的交付前累计收款改为 60% 以上后再上传复审。条款例外审批无法解决信审边界问题。

## 6. 合同案件审批、导出与归档

当 V2 没有 `CREDIT_*`，且所有合同风险均已按证据处理后，使用下列其中一条合适的案件路径：

| 场景 | 操作 |
| --- | --- |
| 无待补材料、无须升级的合同例外 | `reviewer` 在案件详情领取后，点“确认可签约”。 |
| 需要合同案件主管复核 | `reviewer` 点“提交主管复核”；`director` 在“分级审批”阶段点“主管批准可签约”，或“上报最终审批”。 |
| 已上报最终审批，或存在集团财务总监级例外 | `admin` 在“最终审批”阶段点“最终批准可签约”。 |
| 需要补件 | `reviewer` 退回补件；`business` 上传补充/修订文件后重新等待审查。 |

系统会在进入“可签约”前拦截未完成的案件待办、条款审批和待补材料。**这不替代报告内的逐条处置**：有需审批的条款风险时，还必须在报告中发起并完成对应的条款审批。

在报告页选择导出：

- **修订建议稿**：只带人工已采纳、已编辑或已批准的建议；要求当前绑定信审仍是该客户当前已生效版本、没有 `CREDIT_*`、条款审批已通过。
- **原文版**：用于留档比对；不会把它变成可签约的审核结论。
- **双语对照稿**：先在报告内完成 en/vi/ja/es 任一种翻译，再导出；与修订建议稿一样受信审和审批门控。

最后由 `reviewer` 在“可签约”阶段点 **归档**。在案件“流程记录”、报告风险处置、审批记录、导出记录和管理员审计日志中保存本次演练证据。

**停点 F：** 只有在 V2 无 `CREDIT_*`、所需条款审批/补件完成、案件处于“可签约”后，才导出修订建议稿或双语对照稿。

## 7. 最终验收与常见卡点

按 [07-预期结果与验收清单.md](./07-预期结果与验收清单.md) 做最终勾验，并至少留存下列证据：

1. V1 已生效，且包含客户、条件、评估/人工依据、主管与终审意见；
2. 风险合同 V1 的五个 `CREDIT_*` 发现及其证据；
3. 修订合同 V2 的版本对比，显示信审阻断已消除；
4. 合同风险处置、所需审批/补件、导出快照与案件归档记录；
5. 管理员审计日志能对应信审送审/审批、案件动作与导出动作。

| 现象 | 原因与处理 |
| --- | --- |
| “送主管复核”不可点或提示没有依据 | 必须先运行一次评估，并应用合格的生产建议，或在评估异常/建议不适用时保存含理由的人工确认。 |
| 合同申请中没有可选的信审版本 | 客户名称不完全一致、信审尚未 `approved`、信审已过有效期，或登录角色不是 `business`。 |
| 风险合同没有得到预期敞口阻断 | 核对保存的是同一 V1 的 CNY 敞口快照；应收与已入单应分别是 100,000 和 200,000。 |
| 修订稿无法导出 | 检查是否仍有 `CREDIT_*`、合同是否仍绑定当前生效版本、是否有未通过的条款审批；如后来生效了 V2 信审，原 V1 绑定的合同必须重新复审。 |
| “确认可签约”失败 | 案件或报告中仍有开放的审批、待补材料，或当前角色不满足例外审批层级。 |
