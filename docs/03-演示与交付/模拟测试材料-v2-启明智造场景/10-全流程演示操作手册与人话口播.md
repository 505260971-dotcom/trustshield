# 启明智造场景：全流程演示操作手册与人话口播（当前系统版）

> 本文件是现场演示的主手册。它只讲一条完整主线：客户信用审核 → Agent 评估与人工确认 → 分级审批 → 首版合同阻断 → V2 二次额度阻断 → V3 合同复审 → 放行 → 归档与导出。
>
> 所有客户、金额、文件和审批意见均为虚构演练数据，不能作为真实授信结论、法律意见、财务意见或对外合同使用。
>
> 本手册按当前仓库的前后端实现编写，并已在本机用独立临时数据库实际跑通。Agent 首次运行可能需要 2—5 分钟，完整演示建议预留 20—30 分钟。现场不要为了赶时间跳过审批、阻断或修订分支。

## 1. 这场演示要让观众看到什么

一句话说：系统先把客户的信用边界定下来，再拿这条边界去检查合同；合同端可以修订普通风险，但不能把客户级信用阻断“点成通过”。如果 Agent 给出的建议比申请条件更严，也必须回到信用审核流程重新确认，不能在合同页面绕过去。

完整流程如下：

```text
管理员准备账号
  → reviewer 创建信用审核 V1，上传财报和 CRM/ERP 敞口
  → reviewer 运行 Agent，采用建议或记录人工修订依据
  → director 主管复核 → admin 最终审批 → 信用版本已生效
  → business 绑定生效版本，上传 04 首版风险合同
  → reviewer 查看 CREDIT_* 和合同底线风险，退回业务修订
  → business 上传 06 修订合同
  → 若当前信用版本仍不能覆盖合同总敞口：新建信用版本并重新审批
  → 用当前生效信用版本重新发起合同复审
  → reviewer 处理普通风险、补件和条款审批
  → 确认可签约 → 确认已签署并归档 → 导出修订建议稿
```

这里有一个必须讲清楚的现实结果：本地实跑时，Agent 根据财报和 CNY 800,000 既有敞口，把建议额度收紧到 CNY 1,260,000。首版合同改成 CNY 1,000,000 后，合同加既有敞口仍是 CNY 1,800,000，所以 V2 继续触发 `CREDIT_EXPOSURE`。这不是系统出错，而是系统拒绝在合同端绕过新的信用边界。本材料新增 V3：合同金额 CNY 450,000，合计敞口 CNY 1,250,000，可在当前边界内通过信用门禁。

## 2. 角色、菜单和材料

### 2.1 四个演示账号

| 角色 | 系统角色 | 现场主要动作 | 主要菜单 |
| --- | --- | --- | --- |
| 集团财务总监 / 最终审批人 | `admin` | 建账号、最终信用审批、集团级合同审批、看审计 | **审批中心**、**组织与规则**、**系统与集成** |
| 财务审批主管 | `director` | 主管复核信用审核、处理主管级合同例外 | **审批中心** |
| 信用审核专员 | `reviewer` | 创建信审、上传材料、运行 Agent、处理合同风险和放行条件 | **信用审核管理**、**合同审查** |
| 业务申请人 | `business` | 发起合同、上传首版和修订合同、完成业务补件 | **发起合同审查**、**我的申请** |

管理员初始账号由部署环境提供。现场由管理员在 **组织与规则** 创建另外三个演示账号；不要把密码、令牌或真实账号写进材料，也不要用同一个账号代替不同审批角色。

### 2.2 文件只用这三个

- `02-客户财务报告-启明智造.docx`：信用审核中的财报材料。
- `04-首版销售合同-风险.docx`：故意越过信用边界的首版合同。
- `06-修订销售合同-复审.docx`：V2，修正合同文本但保留额度超限，用于展示二次阻断。
- `11-最终销售合同-可签约V3.docx`：V3，金额降至 CNY 450,000、补齐关键条款，用于通过当前信用门禁。

`03-CRM-ERP敞口快照-启明智造.docx` 只作为录入参考，不要把它再当成一份财报上传，否则会让观众误以为系统重复计算同一份事实。

## 3. 开场准备（现场 2 分钟）

### 操作

1. 在仓库根目录启动当前开发服务：

   ```bash
   python dev.py
   ```

2. 浏览器打开 `http://127.0.0.1:5173`。如果演示的是服务器环境，把地址换成现场实际部署地址即可。
3. 以 `admin` 登录，在 **组织与规则** 创建 `reviewer`、`director`、`business`。
4. 顶部 Agent 状态显示未配置时，先到 **系统与集成** 检查模型配置和连接测试；不要在 Agent 未就绪时假装已经完成正式评估。
5. 用 `reviewer` 打开 **信用审核管理**，确认页面可以看到 Agent 评估入口。

### 停点

四个账号都能登录，角色权限不同；Agent 运行环境显示“已就绪”或至少能明确说明为什么未就绪。

### 人话口播

> 我们先把四个岗位分开。业务只能提交材料，审核专员负责核验和处理，主管负责复核，集团财务总监负责最终审批。这样后面每一步是谁做的、为什么做，都能在系统里留下记录。今天的金额和文件都是演示数据，先把流程看清楚，不把它当成真实授信结论。

## 4. reviewer 创建信用审核 V1

### 操作

1. 以 `reviewer` 登录，进入 **信用审核管理**，点击 **新建信用审核版本**。
2. 填写 `01-信审申请单-启明智造.md` 中的核心条件：

   | 字段 | 演示值 |
   | --- | --- |
   | 客户名称 | `启明智造（模拟）有限公司` |
   | 信审业务类型 | `TKM` |
   | 币种 | `CNY` |
   | 最大信用额度 | `1800000` |
   | 最长账期 | `60` 天 |
   | 交付前最低收款 | `40%` |
   | 允许付款方式 | 仅 **银行转账** |
   | VMI/JIT | 不允许 |

3. 申请说明写清楚用途，例如：

   > 为启明智造结构件模具、试制件和量产导入建立客户信用边界，并验证 CRM/ERP 既有敞口与合同金额的合并控制。

4. 点击 **保存评估草稿**，确认列表里出现启明智造 V1。

### 停点

客户、业务类型、金额和条件必须是这一套启明智造数据。不要把其他客户的金额或审批条件混进来。

### 人话口播

> 这里先定的是客户边界，不是某一份合同的结论。我们给启明智造设一个 180 万的总敞口上限，账期最多 60 天，至少先收 40%，付款只接受银行转账，也不允许 VMI/JIT。后面的合同只能在这条边界里谈。

## 5. 上传财报、录入敞口、运行 Agent

### 5.1 上传和录入

1. 打开启明智造 V1 详情，进入 **材料与额度占用**。
2. 选择文档类型 **客户财报**，上传 `02-客户财务报告-启明智造.docx`。
3. 在 CRM/ERP 敞口区录入：

   | 字段 | 值 |
   | --- | ---: |
   | 当前应收 | `350000` |
   | 已入单金额 | `450000` |
   | 逾期金额 | `0` |
   | 最长逾期天数 | `0` |
   | 币种 | `CNY` |

4. 点击 **保存数据**。页面应能看出既有敞口为 `350000 + 450000 = 800000 CNY`。

### 5.2 运行 Agent

1. 进入 **Agent 评估**，点击 **运行 Agent 评估**。
2. 现场展示实时步骤、事实 Claims、来源证据、风险标记和模型状态。不要只等最后一个分数。
3. 评估完成后按结果处理：

   - 如果结果是 production、`model_status=ready_for_reviewer`，没有高风险阻断，而且建议条件正好符合本场景，可以点击 **采用 Agent 建议并提交主管复核**。
   - 如果建议条件比申请更严，进入“审核专员确认与修订”，填写真实的人工依据，选择人工修订后再提交。
   - 如果模型未配置、超时或失败，保留失败记录；只有审核专员已经核对财报和敞口，并明确写下兜底依据时，才可以保存人工兜底。失败本身不能被说成“系统通过”。

4. 现场重点展示 `review_mode`：`agent_recommended` 表示采用建议，`reviewer_adjusted` 表示审核专员修改了建议，`manual_override` 表示在失败或不完整结果下由人明确兜底。

### 本场景的真实分支

本机实跑中，Agent 给出的建议是：额度 `1260000`、可用额度 `460000`、60 天账期、60%预付款、仅银行转账、不允许 VMI/JIT。这个结果有 1 条中等级别的 `EXPOSURE_CAP` 风险提示，但模型状态仍是可供审核专员复核。

现场有两种讲法，必须选一种并讲清楚：

1. **忠实展示模型建议**：采用 126 万，后面的合同会在金额修订后仍可能触发 `CREDIT_EXPOSURE`，按第 8 节重新信审。
2. **直接演示“人工调整后审批”**：在信用审核阶段填写人工依据，将本场景的生效边界调整为 180 万、60 天、60%预付款、银行转账、不允许 VMI/JIT，然后继续审批。人工调整必须进审批记录，不能偷偷改字段。

为了展示当前系统最完整且可现场闭环的控制链，本次实跑先保留 Agent 收紧结果，让 V2 真实触发信用阻断；随后上传不超过可用额度的 V3，而不是篡改已生效的信用边界。

### 人话口播

> Agent 现在做的是读材料、找证据、把事实整理出来。它不是一个“按一下就自动放行”的按钮。这里它根据财报和已经占用的 80 万额度，建议把本次客户上限收紧到 126 万。这个建议可以被审核专员采用，也可以在有依据、有审批的前提下调整；但不能因为合同金额看起来差不多，就把这条风险藏掉。

## 6. director / admin 完成信用审批

### 操作

1. `reviewer` 点击 **提交主管复核**。
2. 切换 `director`，进入 **审批中心**，找到启明智造信用审核，点击 **复核通过**，填写意见：

   > 已复核财报事实、CRM/ERP 既有敞口、Agent 建议及审核专员确认依据，同意按当前信用边界进入最终审批。

3. 如果页面进入 **待最终审批**，切换 `admin`，在 **审批中心** 点击 **最终审批**，填写意见：

   > 已核对客户信用边界及前序审批意见，同意该信用审核版本生效；合同端不得通过例外审批绕过信用条件。

4. 确认信用版本状态变为 **已生效**。只有这一状态能被合同案件绑定。

### 停点

如果还是草稿、待主管复核、待最终审批或被退回，不要继续上传合同。先把信用审批链走完。

### 人话口播

> 合同不是拿着一份申请就能开始的。先由主管复核，再由集团财务总监完成最终审批，系统把当时批准的条件和依据一起冻结下来。后面合同引用的是这个“已生效版本”，不是一组可以随手改动的数字。

## 7. business 上传首版风险合同，reviewer 处理阻断

### 7.1 创建合同案件

1. 切换 `business`，进入 **发起合同审查**。
2. 客户选择 `启明智造（模拟）有限公司`，绑定刚才的已生效信用版本。
3. 合同业务类型选择 **模塑一体**。
4. 上传 `04-首版销售合同-风险.docx`，创建案件并提交审查。
5. 等待案件从 **系统审查中** 进入 **审核员复核**。

### 7.2 查看首版结果

切换 `reviewer`，进入 **合同审查**，打开案件和报告。首版通常会看到以下信用阻断：

- `CREDIT_TERM`：合同 120 天账期超过生效边界；
- `CREDIT_PREPAYMENT`：25%预付款低于生效边界；
- `CREDIT_PAYMENT_METHOD`：出现承兑汇票；
- `CREDIT_DELIVERY_MODE`：出现 VMI/JIT；
- `CREDIT_EXPOSURE`：合同金额加 CRM/ERP 既有敞口超过信用上限。

同时还会有普通合同底线风险，例如关联主体责任、期限、知识产权、取消订单和质保条款。

### 7.3 处理方式

1. 在 **当前版本通关检查** 或“距离签约还差什么”中查看信用阻断、合同风险、待补材料和审批事项。
2. 对任何 `CREDIT_*`，不要点击 **采纳建议**、**确认不适用** 或合同例外审批。系统会拒绝这类动作，这是正确的 fail-closed 行为。
3. 对普通合同风险，可以逐条点击 **处理风险**，选择采纳、编辑后采用或在有依据时确认不适用。
4. 点击 **退回业务补充材料**，说明：

   > 请按启明智造场景修订金额、账期、预付款、付款方式、VMI/JIT、期限、质保、责任和知识产权条款。客户级信用阻断不能在合同端通过例外审批放行。

5. 在首版仍有 `CREDIT_*` 时，尝试 **导出修订建议稿** 应得到 HTTP 409 或页面拒绝提示。这是现场要主动展示的控制证据。

### 人话口播

> 现在系统同时发现了两类问题。普通合同风险可以拿原文出来讨论，必要时按权限审批；但 CREDIT 开头的问题是客户级授权，不能在合同页面点一个“忽略”就消失。这里先退回业务，把合同改回信用边界，再谈后面的审批。

## 8. business 上传 V2，展示额度二次阻断

### 8.1 先上传修订稿

1. 切换 `business`，在案件中点击 **上传修订合同**。
2. 上传 `06-修订销售合同-复审.docx`。
3. 等待当前版本复审完成。若案件处于 **待业务补充材料**，完成页面显示的业务待办；上传成功后系统会重新进入审查。
4. 切换 `reviewer`，打开 **版本对比**，查看首版和修订版的金额、账期、付款节点、期限和条款变化。

### 8.2 预期结果与口播

V2 报告应仍有 `CREDIT_EXPOSURE`：CNY 1,000,000 + CNY 800,000 = CNY 1,800,000，大于当前 Agent 信审额度 CNY 1,260,000。保留这条记录，不要在合同端忽略或例外放行。

> V2 告诉我们一件很重要的事：合同文字改对了，并不代表客户级风险就合规。系统把合同金额和既有敞口一起算，仍然超出 54 万，所以它继续拦住这份合同。这不是失败，是系统把真正的商业边界守住了。

## 9. business 上传 V3 最终合同，进入放行流程

1. 切换 `business`，在同一案件中点击 **上传修订合同**。
2. 上传 `11-最终销售合同-可签约V3.docx`。
3. 等待审查完成，确认页面当前版本为 V3；在版本对比中可同时查看 V1、V2、V3。
4. 切换 `reviewer`，打开 V3 报告。确认没有 `CREDIT_*`：CNY 450,000 + CNY 800,000 = CNY 1,250,000，不超过 CNY 1,260,000。
5. 按页面实际待办处理普通风险、材料事项和条款审批；这些事项不能因为信用门禁已清除而跳过。
6. 全部待办关闭后，点击 **确认可签约**；如页面要求主管或最终审批，分别由 `director`、`admin` 完成。
7. 进入 **可签约** 后，`reviewer` 点击 **确认已签署并归档**。

### 人话口播

> V3 没有动授信额度，也没有申请合同端例外。我们把这笔合同改为 45 万，加上已占用的 80 万，合计 125 万，落在 126 万信用边界内。现在 CREDIT 门禁清除了，接下来仍要把普通合同风险、材料和审批一项项关掉，全部完成后才可以签约。

> 当前本机案件已经保留过一次失败关闭的 V3 预检记录，因此修正后的同名文件在案件列表显示为 V4；该当前版本已实际复审通过。新演练从 V1、V2 开始按本步骤上传时，会显示为 V3。

## 10. 最终合同复审、风险处置和案件放行

以下步骤适用于 V3 已清除 `CREDIT_*` 的当前案件。

### 操作

1. `reviewer` 等待最终合同版本审查完成，打开 **文件、放行条件与协同**。
2. 确认报告中没有 `CREDIT_*`。普通风险仍然可能存在，不能因为信用门禁清了就把整份合同说成“零风险”。
3. 进入 **版本对比**（同一案件有 V1/V2 时），核对：
   - 首版 120 天是否已经变为 60 天以内；
   - 预付款是否达到当前信用条件；
   - 付款方式是否改为银行转账；
   - VMI/JIT 是否删除；
   - 金额与既有敞口合计是否在当前生效上限内。
4. 对普通风险逐条点击 **处理风险**：
   - 有充分证据时选 **采纳建议** 或 **编辑后采用**；
   - 只有能说明为何不适用时才选 **确认不适用**；
   - 规则要求主管或集团财务总监审批时，进入 **审批与补充材料**，由对应角色处理。
5. 处理所有 **补充材料**：业务上传附件后，审核员在材料事项中完成核验；若只是现场说明，也要写入处理意见，不能只口头说“已看过”。
6. 处理完当前版本的风险、材料和条款审批后，点击 **确认可签约**。
7. 如果案件进入 **待主管审批** 或 **待最终审批**，分别切换 `director`、`admin`，使用 **批准可签约** 或 **最终批准可签约**。
8. 进入 **可签约** 后，`reviewer` 点击 **确认已签署并归档**。

### 关于“距离签约还差什么”卡片

这张卡片是诊断和解释工具；最终能否推进，以案件的开放待办、条款审批、补充材料和导出门禁为准。当前系统会把 Agent 的“待人工确认”提示保留在报告中，即使对应补件已经处理，卡片仍可能显示待确认数量；这不等于信用阻断，也不能替代案件放行门禁。现场要同时看：

- 是否还有 `CREDIT_*`；
- 是否还有打开的审批或补件待办；
- 是否可以成功执行 **确认可签约**；
- 修订稿导出是否通过。

### 人话口播

> 现在我们不是简单地把风险数清零，而是把每一条还留在合同里的问题交代清楚：要么按建议改，要么说明为什么不适用，要么交给对应的审批人。系统真正关心的是这些事项有没有责任人、有没有依据、有没有闭环。全部闭环后，才会出现可签约和归档动作。

## 11. 导出交付物和最终验收

在案件已经放行、信用绑定为当前生效版本、没有信用阻断且审批/补件已闭环后，打开最终合同报告的 **导出交付物**：

- **导出修订建议稿**：演示最核心的可交付 DOCX；
- **导出原文留档**：保留原合同版本；
- **导出双语对照稿**：先在报告页完成翻译，再选择语言导出；
- **导出 Markdown / JSON**：用于记录和接口验收，不作为对外合同。

### 现场最终验收清单

- 信用审核版本至少经历了 Agent 评估、审核专员确认和主管/最终审批；
- 首版合同真实出现了多类 `CREDIT_*`，且不能被合同端忽略；
- 首版修订建议稿在阻断未解除时被 HTTP 409 拒绝；
- V2 因额度超限被保留为审计证据，V3 没有直接改旧信用版本；
- 最终 V3 合同版本没有 `CREDIT_*`；
- 普通风险、补件和条款审批有处置记录；
- 案件状态为 **已归档**；
- 修订建议稿导出 HTTP 200 且文件大小大于 0；
- 审计记录能对应信用创建、Agent 运行、审批、合同上传、退回、复审、放行和归档。

### 收尾口播

> 这条链路最后留下的不是一个“模型说可以”的结果，而是一条可以回看的责任链：客户信用条件是谁确认的，合同哪一条越界，业务怎么改的，谁批准了例外，什么时候才允许导出和归档。这样业务拿到的是可执行的合同结果，财务和管理层看到的是完整的风险依据。

## 12. 现场故障处理

| 现象 | 正确处理 | 不要做什么 |
| --- | --- | --- |
| 页面提示 401 | 重新登录当前角色，确认没有把一个角色的页面当成另一个角色 | 不要复制别人的 token |
| Agent 未就绪 | 到 **系统与集成** 查看模型配置和连接测试；必要时展示失败关闭 | 不要把未运行说成已通过 |
| Agent 运行很慢 | 看实时步骤，等待完成；首次远程调用可能需要几分钟 | 不要连续重复点击运行 |
| 首版导出返回 409 | 打开信用阻断、材料和审批事项，按流程修订 | 不要改 URL、数据库或直接导出 |
| V2 仍有 `CREDIT_EXPOSURE` | 上传金额不超过 CNY 460,000 的 V3；如业务必须保留 CNY 1,000,000，则新建信用审核版本并重新审批 | 不要在合同端忽略、采纳或审批 CREDIT 风险 |
| 普通风险处理后仍有待办 | 查看 **审批与补充材料**，由对应角色完成审批或补件 | 不要只在口头上说“处理过了” |
| “距离签约还差什么”仍显示待确认 | 以开放待办、信用阻断、放行动作和导出门禁为准；卡片是诊断信息 | 不要把诊断卡片数字当成最终审批结果 |
