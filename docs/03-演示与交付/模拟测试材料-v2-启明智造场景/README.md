# 信盾 TrustShield 信审-合同审核模拟材料包 v2：启明智造场景

> 版本：v2.0 ｜ 场景日期：2026-07-31 ｜ 数据属性：全部为虚构、脱敏的演练数据。

本材料包用于演练“客户信审 → 授信生效 → 合同首审阻断 → 合同修订复审 → 分级审批 → 签约归档”链路，重点验证 **TKM 信审边界与模塑一体合同底线规则的联动**。

本材料不能作为真实授信结论、法律意见、财务意见或对外合同使用。所有金额、主体、评级、财务数据和审批意见均为模拟内容。

## 三、推荐角色

| 演练角色 | 系统角色 | 主要动作 |
| --- | --- | --- |
| 系统管理员 / 集团财务总监 | `admin` | 创建成员；必要时完成信审最终批核和集团级合同审批。 |
| 信用审核专员 | `reviewer` | 创建信审、上传财报、录入敞口、运行评估、确认条件、送主管复核、处理合同风险。 |
| 财务审批主管 | `director` | 复核信审 V1；处理主管级合同审批或退回。 |
| 业务经办人 | `business` | 发起合同申请、上传首版合同、响应补件、上传修订合同。 |

从空库开始时，只有管理员会被初始化。请由管理员创建其他演练账号；不要把真实账号、密码或令牌写入材料包。

## 四、标准闭环

```text
reviewer：创建信审 V1，上传财报和敞口快照
    ↓
reviewer：运行量化评估，确认 Agent 建议或记录人工报送依据
    ↓
director / admin：完成信审审批，V1 变为“已生效”
    ↓
business：绑定 V1，上传 04 首版风险合同
    ↓
系统：识别 CREDIT_TERM / CREDIT_PREPAYMENT / CREDIT_PAYMENT_METHOD
      CREDIT_DELIVERY_MODE / CREDIT_EXPOSURE，以及合同底线风险
    ↓
reviewer：确认信审阻断不能在合同端放行，要求业务修订合同
    ↓
business：上传 06 修订合同，系统生成当前版本 V2
    ↓
reviewer：检查版本对比、处理合同风险并提交后续审批
    ↓
director / admin：按实际门禁完成合同审批
    ↓
reviewer：确认可签约并归档
```

## 五、使用规则

1. 信审 V1 必须先达到 `approved` / “已生效”，合同才能绑定它。
2. `CREDIT_*` 是客户商业边界阻断，不能通过合同例外审批、忽略或人工改成通过。
3. 首版合同的金额、账期、预付款、付款方式和交付模式均故意越界；不要直接把它审批为可签约。
4. 修订合同保持原信审 V1 不变，通过降低合同金额、提高预付款、缩短账期、改为银行转账并删除 VMI/JIT 来消除阻断。
5. 如果 Agent 未配置、超时或材料未形成完整 Claims，必须走失败关闭或有依据的人工确认，不得把失败当成自动通过。
6. 实际上传和录入参考材料统一使用本目录中的 DOCX；不要把同一材料重复计入业务事实。

## 六、场景通过标准

最终至少应能证明：

- 启明智造 V1 已完成信审审批并变为“已生效”；
- 首版合同至少出现五类 `CREDIT_*` 信审阻断；
- 首版合同的合同底线风险被定位到原文并进入人工处理；
- 修订合同 V2 的总敞口为 CNY 1,800,000，不超过 V1 上限；
- V2 不再出现 `CREDIT_*`；
- 版本对比、审批、导出和归档均有流程记录；
- 审计日志能够对应信审创建、审批、合同上传、风险处置和案件流转。
