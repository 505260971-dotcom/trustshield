# 启明智造场景：V3 最终合同通过说明

> 对应文件：`11-最终销售合同-可签约V3.docx`  
> 场景日期：2026-08-03  
> 数据属性：全部为虚构、脱敏的演练数据，不得作为真实合同或授信结论使用。

## 1. 为什么需要 V3

V2 已经把账期、预付款、承兑付款和 VMI/JIT 等文本问题修正，但它的合同金额仍是 CNY 1,000,000。当前 Agent 已核验财报并给出的信用边界是总额度 CNY 1,260,000；客户已有 CNY 800,000 的应收和已入单敞口。因此 V2 进入合同后的总敞口为 CNY 1,800,000，仍超出 CNY 540,000，必须继续被 `CREDIT_EXPOSURE` 阻断。

V3 不修改信用边界，也不在合同端申请例外。它把本合同金额调整为 CNY 450,000，并将 V2 中容易触发人工确认的价格、取消订单、责任和期限条款写得更明确，从而提供一份可以在当前生效信审边界内继续推进的最终合同文本。

## 2. V3 的通过计算

| 项目 | 金额 / 条件 |
| --- | --- |
| 当前信用审核总额度 | CNY 1,260,000 |
| CRM/ERP 既有敞口 | CNY 800,000 |
| V3 合同金额 | CNY 450,000 |
| 签订后总敞口 | CNY 1,250,000 |
| 剩余可用额度 | CNY 10,000 |
| 最长账期 | 交付后 60 天 |
| 交付前最低收款 | 60% |
| 付款方式 | 银行转账 |
| VMI/JIT | 明确不采用 |

计算式：`800,000 + 450,000 = 1,250,000 ≤ 1,260,000`。

## 3. 上传和复审步骤

1. 用 `business` 登录，打开此前已经有 V1 / V2 记录的启明智造合同案件。
2. 点击 **上传修订合同**，选择 `11-最终销售合同-可签约V3.docx`。
3. 等待系统完成审查。确认当前版本显示为 **V3**，而不是覆盖或删除 V1 / V2。
4. 用 `reviewer` 打开 V3 审查报告，先看“当前版本通关检查”或“距离签约还差什么”。
5. 确认报告中没有 `CREDIT_*` 风险，特别是没有 `CREDIT_EXPOSURE`。报告中的额度应体现合同 CNY 450,000、既有敞口 CNY 800,000、合计 CNY 1,250,000。
6. 按页面中实际仍打开的普通风险、材料事项和审批事项逐项处理。只有全部待办关闭后，再点击 **确认可签约**。
7. 如页面路由要求主管或最终审批，分别由 `director`、`admin` 完成审批；进入 **可签约** 后，再由 `reviewer` 确认已签署并归档。

## 4. 预期结果

- V1：首版风险合同，展示五类 `CREDIT_*` 以及合同底线风险；不得放行。
- V2：合同条款已修订，但金额 CNY 1,000,000 使总敞口达到 CNY 1,800,000；继续被额度门禁阻断。
- V3：合同金额降为 CNY 450,000，总敞口 CNY 1,250,000；信审门禁清除，进入普通风险处置、审批、导出和归档流程。

> V3 “能通过”准确指的是：它满足当前信用边界并不再触发 `CREDIT_*`。是否立即可签约仍由页面上的普通风险、补件和审批待办决定；这些事项必须如实关闭，不能为了演示跳过。

> 当前本机案件的说明：在完成这份材料前，系统曾上传一份字段抽取失败的 V3 预检稿，系统按失败关闭原则保留了该记录。修正字段兜底和质保条款后，重新上传同一份 `11-最终销售合同-可签约V3.docx`，当前页面显示为 **V4**，总体结论为“通过”，`signable=true`，风险、待人工确认、补件和审批待办均为 0。新的空场景按本说明操作时，这份文件会直接成为 V3；当前显示为 V4 只是为了保留失败预检的审计版本。

## 5. 现场口播

> V2 已经把合同文字改得比较规范，但系统不会只看文字。它把 100 万合同和客户已经占用的 80 万一起算，总风险敞口是 180 万，而当前信用边界只有 126 万，所以 V2 仍然不能签。
>
> 现在上传 V3。这里没有偷偷改授信，也没有在合同端点例外：我们把本次合同调整到 45 万。加上已有 80 万，合计 125 万，还留出 1 万的额度空间。系统确认信用门禁清除后，才继续处理普通合同事项和审批。这就是“合同修订回到已批准信用边界”，而不是“合同页面绕过信用审核”。
