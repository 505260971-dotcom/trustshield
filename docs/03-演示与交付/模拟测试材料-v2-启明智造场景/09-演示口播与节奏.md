# 启明智造场景：演示口播与节奏

> 本文件是短口播参考，不是完整操作依据。完整主流程和 V2 二次阻断、V3 通过复审路径请使用同目录的 `10-全流程演示操作手册与人话口播.md`。若要实际跑完 Agent、审批和合同导出，建议预留 20—30 分钟；不要为了节省时间跳过信审审批或直接把首版合同标成通过。

## 1. 开场：说明系统控制点（约 30 秒）

可用口播：

> 今天演示的不是单纯的合同风险扫描，而是客户级信审条件如何成为合同审核的前置边界。启明智造先完成授信审批，再上传合同；首版合同会故意越过额度、账期、预付款和交付模式边界，系统会阻断它。只有合同修订回边界并重新审查后，案件才可能继续签约。

## 2. 信审申请和证据（约 1 分钟）

展示：

- **信用审核管理** 列表；
- V1 条件：CNY 1,800,000、60 天、40%、仅银行转账、不允许 VMI/JIT；
- 财报上传和文字资产状态；
- CRM/ERP 敞口 800,000。

可用口播：

> 这里的额度不是孤立地看本次合同，而是要叠加客户当前应收和已入单金额。启明智造已经有 800,000 的既有敞口，所以首版 1,200,000 的合同会直接超过客户总敞口上限。Agent 如果根据财报再把额度收紧，后面修订合同仍可能被 `CREDIT_EXPOSURE` 拦住，这时要重新走信用审核。

## 3. Agent 与人工责任（约 45 秒）

展示：

- 量化评估运行状态；
- Claims/来源证据/审计详情；
- 审核专员确认或人工修订依据。

可用口播：

> Agent 可以整理证据和给出建议，但不能代替审核专员的报送确认，也不能在模型失败时伪造授信结论。系统要求每个修改建议或人工兜底都有明确理由。

## 4. 两级信审审批（约 45 秒）

展示：

- reviewer 送主管复核；
- director 复核；
- admin 最终批核；
- V1 变为已生效。

可用口播：

> 合同端只能选择已生效的信审版本。草稿、退回、待审批版本都不能作为合同的商业边界。

## 5. 首版合同阻断（约 1.5 分钟）

展示：

- 发起合同并绑定 V1；
- 首版合同金额、120 天账期、25%预付款、承兑、VMI/JIT；
- 案件门禁；
- 报告左侧问题条款导航；
- `CREDIT_*` 发现。

可用口播：

> 这里同时出现了合同底线风险和客户信审阻断。两者的处理方式不同：合同底线可以修订或按权限审批，但 CREDIT 阻断不能在合同端忽略。因为它表达的是客户级商业授权，不是某一条合同文字的例外。

## 5.1 展示“距可签约还差什么”（约 30 秒）

展示审查报告顶部的“距可签约还差什么”卡片：

- 当前合同后总敞口 2,000,000，信审上限 1,800,000；
- 账期、交付前收款、付款方式和 VMI/JIT 分别越过信审边界；
- 系统把事项分成“合同可修订”和“必须重新信审”；
- 首版的多项 CREDIT 阻断可以通过修订合同回到信用边界；但本机 Agent 实际额度是 CNY 1,260,000，V2 的 CNY 1,000,000 金额仍会超限。

可用口播：

> 这里系统不只告诉业务“不能签”，还计算出最小修订路径。按照当前 126 万额度和 80 万既有敞口，合同金额最多只能保留 46 万；V3 使用 45 万。账期回到 60 天以内，交付前收款至少 60%，付款改为银行转账，并删除 VMI/JIT。系统不会给出一个看似可行、实际却超过额度的合同修改建议。

## 6. 修订和复审（约 1.5 分钟）

展示：

- 业务上传 V2，再上传 V3；
- 当前版本变化；
- 版本对比；
- V2 的金额 1,000,000 + 既有敞口 800,000，仍被拦截；
- V3 的金额 450,000 + 既有敞口 800,000 = 1,250,000，在 CNY 1,260,000 边界内；
- 付款和交付模式回到信审边界。

可用口播：

> V2 的文字虽然改好了，但总金额仍越过当前信用边界，所以不能说它通过。V3 把合同调整为 45 万，不改授信、不走合同端例外，直接回到当前 126 万信用边界内。信用门禁清除后，再把普通风险、补件和审批闭环。

## 6.1 可选补充：客户级动态敞口守卫（不属于本次主流程）

进入客户档案，展示“客户级动态敞口守卫”：

- 当前 Agent 信审上限 1,260,000；
- CRM/ERP 既有敞口 800,000；
- 当前在途 V3 合同 450,000；
- 合同计入后剩余可用敞口为 10,000；
- 模拟新增 100,000 后，系统立即显示超出信审上限并提示需要重新信审。

可用口播：

> 这部分是客户工作台的补充能力，不是今天的主流程验收点。合同审查解决的是这一份合同，但客户风险不能只看单份合同；如果时间充足，再展示既有敞口和在途合同的模拟，不要用它替代前面的信用审核和合同复审。

## 7. 收尾：审批、导出和审计（约 45 秒）

展示：

- 合同风险处置；
- 审批/补件门禁；
- 导出按钮；
- 案件流程记录和审计日志。

可用口播：

> 当 V3 不再被信审阻断，且合同风险、补件和审批门禁全部闭环后，系统才允许导出交付物并归档。整个链路从信审、合同到审计都能追溯到具体责任角色。

## 8. 演示中的三个提醒

1. 不要把模型未配置或评估失败说成“系统通过了”；应明确展示失败关闭和人工责任。
2. 不要在首版合同上点击“确认可签约”来节省时间；阻断本身就是本次演示的核心证据。
3. 不要只展示最终 V3，要保留 V1 首审、V2 额度阻断、版本对比和审批记录，才能证明系统控制真正发生过。
