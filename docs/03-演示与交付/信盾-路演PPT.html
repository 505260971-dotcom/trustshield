做完就结束了：不感知客户授信边界、没有审批闭环、结论无法追溯。命题里「信审与合同评审一体化」恰好是它的盲区。

TrustShield · 我们的解法

先授信定边界，再合同审条款

合同案件强制绑定已生效信审；越界不是「提示」，是系统级阻断——合同端放不了，导出可签约稿前还会再查一遍。

🚫 越界不可绕过

信审越界不能「忽略」、不能走普通例外审批；必须先更新信审、基于新版本复审。

🧭 提交前就能预判

客户工作台「模拟下单」测算可用额度——业务签之前就知道这笔会不会越界。

🛡️ 材料不足就不给结论

信审 Agent 核验失败直接说「给不了」，绝不编一个授信数字。

真实的边界长这样（系统内已生效信审实例）：客户额度 ¥1,000,000 · 账期 90 天 · 付款方式 仅银行转账 · VMI/JIT 允许 —— 合同里出现超出这些数字的条款，就是阻断项。

底线不靠模型拍脑袋

账期、额度、VMI、间接损失——能不能签由确定性代码裁决，模型只出候选与建议。

为什么：可解释、可单测、可回归

原文不出内网

敏感字段占位符流转全程，映射加密持久化，翻译外发前强制校验。

为什么：命题「脱敏 + 自动还原」的完整闭环

失败即拒，不硬编

信审 ReAct 16 步预算封顶；核验失败写明缺什么，不产出授信建议。

为什么：编出来的授信比不给建议危险

检索挂了就明说

词法召回 →（可选 Embedding 融合）→ rerank 精排；rerank 不可用不悄悄降级。

为什么：杜绝「看着有依据、其实没检索」
